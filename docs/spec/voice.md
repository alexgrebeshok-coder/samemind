# Спецификация 0.16 — голосовой контур

> Версия: draft 0.16-spec · Статус: спецификация (кода нет) · Топик: `samemind-l10-specs`
> Связано: `docs/spec/control-center.md` (раздел «Голос»), `docs/spec/ambient-vision.md`,
> `docs/ui-spec.md` (существующий дашборд, на который опирается экран подтверждения).

## 0. Постановка задачи

Голос — самый быстрый канал «спросил — ответил», но и самый опасный: неточность
распознавания + необратимые действия = катастрофа. Прототип уже был и оставил уроки,
которые здесь зафиксированы как **проверяемые требования**, а не как пожелания.

Принцип, из которого выводится всё ниже: **голос не даёт привилегий**. Всё, что через
голос можно сделать, можно сделать и через экран. Голос лишь меняет скорость ввода и
формат вывода, но не набор разрешённых действий и не их обратимость.

## 1. Жёсткие границы (выведены из уроков прототипа)

Эти правила действуют во всех режимах без исключения. Нарушение любого — блокер релиза.

**Г1. Распознавание ВСЕГДА неточно.** Уверенность распознавания — обязательный сигнал.
Если уверенность ниже порога (см. §4), система обязана **переспросить**, а не
догадываться. Угадывание намерения из нечёткой речи — дефект, а не функция.

**Г2. Неоднозначная речь не запускает необратимое.** Из реплики с низкой уверенностью или
несколькими равновероятными интерпретациями система **не имеет права**:
- отправить наряд движку (fleet assign);
- создать долговременную память (inbox write);
- изменить план или статус задачи (ledger append с фазой `done`/`start`);
- совершить любое внешнее действие (публикация, пуш, отправка сообщения, трата).

Вместо этого — карточка уточнения на экране и/или голосовой вопрос.

**Г3. Ограниченная задержка.** Задержка ответа измеряется и ограничивается (см. §6,
наблюдаемость). Если задержка превышает бюджет — пользователь видит и слышит явное
«обрабатываю, подожди», а не тишину. Тишина дольше N секунд = индикация статуса.

**Г4. Личность и факты неизменны.** Голосовой помощник не имеет права:
- молча сменить личность, тон или имя в угоду разговору;
- выдумать факт исполнения («готово, отправил») без артефакта на диске;
- скрывать сбой за дружелюбной фразой.

Любой словесный итог должен соответствовать наблюдаемому статусу в системе.

## 2. Конвейер

Линейная цепочка с явными границами между стадиями. Каждая стадия эмитит событие
наблюдаемости (§6) и может быть измерена отдельно.

```
микрофон
  → [детектор речи] (VAD: тишина/речь/конец реплики)
  → [локальное распознавание] (ASR на устройстве, текст + уверенность)
  → [гейт намерения и уверенности]
       │
       ├─ уверенность < порога  → голосовой/экранный переспрос
       ├─ намерение = вопрос     → маршрутизация в очередь ответов → голосовой/визуальный ответ
       └─ намерение = задача     → карточка подтверждения на экране (§3) → маршрутизация на движок
  → [синтез речи] (TTS) для короткого итога
```

Требования к конвейеру:

- **Детектор речи (VAD)** работает локально. Его задача — определить границы реплики
  (начало/конец), а не содержание. Ложные срабатывания (шум принят за речь) допустимы и
  обрабатываются гейтом как «нет уверенности → нет действия».
- **Распознавание (ASR) локально.** Сырое аудио не покидает устройство (см. §5).
  На выходе: текст + оценка уверенности (`0..1`) на уровне всей реплики и, по возможности,
  на уровне ключевых слов.
- **Гейт намерения и уверенности** — единственная точка, где решается «вопрос или задача».
  Этот гейт однозначно консервативен: при сомнении — переспрос, не действие.
- **Никаких скрытых переходов.** Переход из «слышу» в «понял» и из «понял» в «действую» —
  отдельные наблюдаемые шаги с разными задержками.

## 3. Модель взаимодействия

Базовый цикл из пяти шагов. Отклонения от него возможны только в безопасных режимах (§4) и
только в сторону *меньших* действий, не больших.

```
сказал → подтвердил на экране → исполнилось → показан статус → короткий голосовой итог
```

Пошагово:

1. **Сказал.** Пользователь произнёс реплику. Система показывает живую расшифровку
   (даже черновую) на экране — чтобы было видно, что именно расслышано.
2. **Подтвердил на экране.** Для задач (в отличие от вопросов) карточка подтверждения
   показывает: расслышанный текст, распознанное намерение, целевую сущность, planned
   действие, **критерий `verify`** (обязателен — §7.1), **карантин/matches** если
   сканер сработал, и **issuer vs engine** при assign. Пользователь явно принимает
   (`Enter`/кнопка/чёткое голосовое «да», см. §5) или отклоняет. Для безобидных
   запросов статуса подтверждение не нужно.
3. **Исполнилось.** Действие выполнено движком/системой. Статус исполнения наблюдаем
   (летопись/артефакт), см. §4 отображения намерений.
4. **Показан статус.** На дашборде (контрольный центр, раздел «Голос») — карточка
   «что запросили → что произошло» с доказательством (ссылка на событие летописи).
5. **Короткий голосовой итог.** TTS озвучивает одну-две фразы. Длинные ответы — только
   визуально: таблица флота, список блокеров, тело концепта — на экран, не в уши.

**Правило длины голосового ответа:** если ответ не помещается в ~2 коротких предложения —
он показывается визуально, а голосом звучит только сводка («3 блокера, детали на экране»).
Голос для деталей таблиц — это антипаттерн.

## 4. Режимы

Четыре режима, переключаемых явно. Активный режим виден на экране и озвучивается при
переключении.

| Режим | Что делает | Что уходит в LLM | Что остаётся локально |
|---|---|---|---|
| **Приватный разговор** | Ответы на вопросы по памяти/знаниям, без побочных действий | Текст реплики (после гейта уверенности) | Сырое аудио, всё, что не подтверждено |
| **Захват задач** | Создание inbox/нарядов из речи — только через подтверждение | Текст реплики + контекст сущности | Сырое аудио, черновики до подтверждения |
| **Статус флота** | Чтение `/api/handoff`, `/api/fleet`, `/api/ledger` голосом | Минимум: только если нужен синтез/рефразинг | Большая часть — локальные данные бандла |
| **Управляемая отправка** | Действия, меняющие состояние (assign, publish, send) | Только после подтверждения, текст действия | Подтверждение, артефакт, летопись |

Требования:

- **Менеджер не может сменить режим за пользователя** молча. Смена режима — наблюдаемое
  событие с голосовым/визуальным подтверждением.
- В режиме **Приватный разговор** побочные действия запрещены архитектурно — гейт задач
  просто не запускается. Это не настройка «можно отключить», это свойство режима.
- Что именно текстом уходит в LLM — явно перечислено выше и не расширяется молча.

## 5. Кнопки и явное согласие

Контроль всегда у пользователя. Минимальный набор органов управления (экран + горячие
клавиши + голосовые команды):

- **Mute** — микрофон физически/программно выключен, индикатор горит, система не слышит.
- **Пауза** — приостановка прослушивания на время (не выключение устройства).
- **Стоп текущей задачи** — прервать исполняющееся действие, если оно ещё обратимо.
  Необратимые (отправленные) — отметить «уже ушло, отменить нельзя».
- **Передать движку по имени** — явное указание исполнителя в реплике («отдай курсору»).
  Без явного имени — маршрутизация по правилам флота.
- **Принять / Отклонить** — для карточки подтверждения (§3).

**Согласие никогда не выводится из разговорного мусора.** Это отдельное требование (Г1):
«ага», «угу», «ну да», «наверное», «давай», кивки/паузы — **не являются** подтверждением.
Подтверждение — либо явная кнопка/`Enter`, либо чёткая голосовая команда из белого списка
(«да, подтверждается», «выполняй»). Белый список поддерживаются и задокументированы.

Сомнение в том, было ли подтверждение — трактуется как **отсутствие** подтверждения.

## 6. Наблюдаемость

Голосовая система, которая не может показать, что случилось, доверия не заслуживает.
Каждая стадия конвейера должна эмитить метрику.

**Канал телеметрии — открытый вопрос, а не решённое.** Существующий SSE-поток
`/api/events/stream` (`tools/lib/ui-server.mjs`, `createLedgerStreamHub`) **не подходит**
для метрик голоса: он жёстко привязан к одному файлу — `ledger/events.jsonl` — и
парсит каждую строку как событие летописи (формат `{topic, phase, action, …}`).
Метрики задержек в нём означали бы мусор в append-only летописи, а `deriveLedgerCards`
в `tools/board.mjs` тут же синтезировала бы из них карточки на доске. Голосу нужен
**отдельный канал** (свой SSE-эндпоинт, отдельный файл событий или иное) — его форма
остаётся открытым вопросом (§12). До его решения метрики видны только в логах и на
экране «Голос» (через сервис голоса, не через сервер дашборда).

Минимальный набор измерений (цели, подлежащие замеру на целевом железе, а не контракты):

| Метрика | Что измеряет | Цель (draft, подлежит замеру) |
|---|---|---|
| `asr_latency_ms` | От конца реплики до текста | цель: p95 < 1500 мс на устройстве |
| `intent_latency_ms` | От текста до решения гейта | цель: p95 < 800 мс |
| `route_latency_ms` | От решения до старта действия | цель: p95 < 500 мс |
| `first_response_ms` | От конца реплики до первого отклика (любого) | цель: < 1000 мс (иначе индикация «обрабатываю») |
| `confirm_latency_ms` | От подтверждения до исполнения | зависит от действия, но наблюдаемо |

Целевое железо для замеров: Apple M1 Pro, macOS 26, где доступен системный
SpeechAnalyzer; альтернатива для потока — Parakeet на Neural Engine. Бюджеты выше —
гипотезы, требующие калибровки на реальном движке распознавания, а не контракт.

События, обязательные к записи (не как метрики, а как факты):
- **Сбои** на любой стадии (VAD/ASR/гейт/маршрут/TTS).
- **Прерванные реплики** (пользователь перебил систему или отменил).
- **Поправки пользователя** («нет, я сказал X, не Y») — отдельный класс, они учат систему,
  что её уверенность была ложно высокой.
- **Переспросы** гейтом — сколько раз по одной реплике, на каком слове.

Все эти данные видны на экране «Голос» в контрольном центре (`docs/spec/control-center.md`),
а не только в логах. Разработчик/пользователь должен видеть историю текущей сессии как
ленту карточек: «услышал → уверенность → намерение → действие/вопрос → итог».

## 7. Отображение намерений на сущности samemind

Голос не создаёт новый чат-лог. Распознанные намерения отображаются на **существующие**
сущности samemind — это сохраняет единое пространство памяти и наблюдаемости.

| Речевой шаблон (пример) | Намерение | Целевая сущность | Действие |
|---|---|---|---|
| «что осталось?» / «на чём я остановился» | запрос контекста | `handoff` | чтение `buildHandoffModel`, голосовой свод + визуал |
| «продолжи задачу X» / «отдай Y курсору» | запуск работы | `fleet assign` / `ledger append(start)` | карточка подтверждения → assign |
| «запиши решение: …» | захват факта | `inbox/<agent>.md` | карточка подтверждения → inbox write |
| «что в блокере по Z» | запрос статуса | `ledger openFailures` | чтение, голосовой ответ |
| «покажи флот» | запрос статуса | `fleet status` | чтение, визуальный ответ (голосом — только свод) |

Правила:
- **Чтение (запрос статуса)** — не требует подтверждения, не меняет состояние.
- **Запись/действие (assign, inbox, done)** — всегда через карточку подтверждения (§3).
- Намерение, не попавшее ни в одну категорию и имеющее низкую уверенность — переспрос,
  не «лучшее предположение».

### 7.1 Ограничения ядра (из кода — обязательны для голосового UI)

Три жёстких следствия существующих модулей. Карточка подтверждения и голосовой
маршрут **не могут** их обойти «для удобства».

**1. `verify` обязателен при выдаче наряда** (`tools/lib/fleet.mjs` →
`buildAssignment`). Сообщение при отсутствии: *«an assignment without a
verification step is a wish, not a task»* — вызов без `verify` бросает.
Значит отдать работу голосом, **не назвав критерий проверки, нельзя**:
карточка подтверждения **обязана** спросить `verify` (или подставить явно
согласованный шаблон проверки, который пользователь видит и подтверждает),
а не молча слать assign без поля.

**2. `ref` — ключ идемпотентности** (`tools/lib/ledger.mjs` → `appendEvent`).
При том же `ref` повторный append — **no-op** (`{ deduped: true, event }`),
вторая строка не пишется. `memory_fleet_assign` прокидывает `ref` в ledger
(см. MCP-схему: voice utterance id). Голос **обязан** чеканить устойчивый id
реплики (один id на одну фразу / одно подтверждение) и передавать его как
`ref`. Иначе переслышанная или повторно подтверждённая фраза создаст **дубль**
назначения. Без `ref` dedup не работает — plain append каждый раз.

**3. Сканер инъекций сработает на невинной диктовке** (`tools/lib/injection.mjs`
→ `scanForInjection`). Паттерн `run-execute-command` ловит, в частности,
формулировки вроде «run … script» / «execute … command» — в т.ч. обычную
речь «запусти скрипт …». Текст **не отбрасывается**: помечается
`quarantine: true` + `matches`, в ledger/inbox уходит с флагом (тот же
контракт, что у `memory_write_inbox` / `buildEvent`). Карточка подтверждения
**обязана показывать карантин** (и список matches), иначе человек увидит
«принято» и удивится метке quarantine в летописи.

**Дыра атрибуции (и намеренный обход):** `memory_fleet_assign` пишет
`actor` = **целевой движок** (`assignment.engine`), а не выдавший. Иначе
сломается heartbeat: `fleet status` считает «последний раз видели» по
`actor` — если в actor попал директор/голос, молчащий engine выглядел бы
живым. Выдавший фиксируется отдельно: `SAMEMIND_AGENT` (sanitize) → маркер
`[by <issuer>]` **в тексте `action`**, если issuer ≠ engine; при
self-assign маркер опускается. Голосовой UI / карточка должны показывать
оба: **кому** выдали (engine) и **кто** выдал (issuer), не подменяя actor
на «голос» или директора.

Связано: `docs/fleet.md`, `docs/voice-companion.md`, тесты
`tools/fleet.test.mjs` (секции R: ref / issuer / heartbeat).

## 8. Режимы отказа (что система делает, когда не может)

| Ситуация | Поведение |
|---|---|
| Уверенность ASR ниже порога | Переспрос: «не расслышал, повтори?» — на экране черновой текст |
| Несколько равновероятных намерений | Карточка выбора на экране, голосом — перечисление вариантов |
| TTS недоступен | Только визуальный ответ; индикатор «голос недоступен» |
| ASR недоступен | Режим разговора выключен, ввод текстом; индикатор |
| Действие зависло (превышен бюджет) | «обрабатываю дольше обычного», статус виден, опция «отмена» если обратимо |
| Ложное подтверждение из мусора | Не считается подтверждением (Г1, §5); повторный запрос явного «да» |

Правило единообразия: **отказ всегда наблюдаем и озвучен/показан**. Тихая деградация —
дефект. Пользователь всегда знает, в каком состоянии система: слышит / не уверена /
ждёт подтверждения / исполняет / не может.

## 9. Приёмка (критерии, по которым спецификация считается реализованной)

Каждый пункт — проверяемый прогоном или инспекцией.

- [ ] Конвейер из §2 реализован; каждая стадия эмитит событие наблюдаемости.
- [ ] Уверенность ASR учитывается гейтом; ниже порога — переспрос, не догадка (Г1).
- [ ] Никакое необратимое действие (Г2 список) не запускается без подтверждения.
- [ ] Бюджеты задержек (§6) измерены и не превышены на тестовом корпусе реплик.
- [ ] Цикл из §3 (сказал → подтвердил → исполнилось → статус → итог) работает на demo-сценариях.
- [ ] Четыре режима (§4) различимы, переключение наблюдаемо.
- [ ] «Разговорный мусор» (§5 список) не трактуется как подтверждение — протестировано на корпусе.
- [ ] Намерения (§7) отображаются в существующие сущности, отдельного чат-лога нет.
- [ ] Assign без `verify` невозможен (гейт UI + отказ `buildAssignment` / MCP).
- [ ] Повтор той же реплики с тем же `ref` не создаёт второй `start` в ledger.
- [ ] Карантин (`quarantine` / matches) виден на карточке подтверждения до «да».
- [ ] Actor assign = engine; issuer виден как `[by …]` / отдельное поле UI, heartbeat не врёт.
- [ ] Все режимы отказа (§8) дают видимый/слышимый сигнал, а не тишину.
- [ ] Тесты голосового контура — на записанных аудиофикстурах, не на живом микрофоне
      (см. `docs/spec/ambient-vision.md` §12 — тот же принцип: живая съёмка только с согласия).

## 10. Чем это НЕ является

- Не замена экранного интерфейса, а ускоренный канал для части действий.
- Не «умный ассистент, который всё решает сам» — подтверждение на необратимое обязательно.
- Не скрытая запись разговоров — сырьё локально, хранение минимально (см. §4–5).
- Не инструмент для молчаливой смены личности или тона (Г4).

## 11. Где хранится состояние

Все пользовательские настройки голоса — режимы (§4), пороги уверенности (§4, §12),
белый список подтверждений (§5), кулдауны и таймауты — живут в **`.samemind/config.json`**
в корне бандла. Это уже существующий дом конфигурации (см. `tools/lib/projection-config.mjs`:
`schema_version`, двухуровневое слияние global←project, чтение никогда не пишет,
атомарная запись через `atomicWriteFileSync`). Раздел голоса (например, `voice: { mode,
thresholds, … }`) добавляется по тем же правилам: project-уровень перекрывает global,
отсутствие раздела — значения по умолчанию из этой спеки. Запись настроек — через
CLI/setup (как `migrateProjectionConfig`), не молчаливо из произвольного чтения.

## 12. Открытые вопросы (владельцу)

- Порог уверенности ASR (draft: реплика < 0.6 → переспрос, ключевое слово < 0.5 → переспрос
  по слову) — требует калибровки на реальном движке распознавания.
- Белый список голосовых подтверждений — начальный набор задан, расширение требует явного
  решения (расширять небезопасно: «угу» и «ага» уже в мусоре).
- Будет ли TTS локальным или внешним — влияет на приватность (§4, что уходит с устройства).
- **Отдельный канал телеметрии (§6):** форма — свой SSE-эндпоинт, отдельный файл событий,
  или иной. Существующий `/api/events/stream` к этому не годится (привязан к
  `ledger/events.jsonl`, см. §6). Требует решения до реализации экрана «Голос».
