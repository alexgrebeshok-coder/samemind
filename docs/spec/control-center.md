# Спецификация 0.16 — центр управления

> Версия: draft 0.16-spec · Статус: спецификация (кода нет) · Топик: `samemind-l10-specs`
> Связано: `docs/ui-spec.md` (существующий дашборд v1), `tools/lib/ui-server.mjs` (его сервер),
> `docs/spec/voice.md`, `docs/spec/ambient-vision.md`.

## 0. Что это и чем не является

Центр управления — это **расширение существующего локального дашборда** (`samemind ui`,
см. `docs/ui-spec.md` и реализацию `tools/lib/ui-server.mjs`), а не новое приложение.
Дашборд v1 уже имеет четыре экрана: Overview / Memory / Fleet / Projects. Эта спецификация
добавляет к ним новый видовой слой и экран под голосовой контур, не ломая существующих.

Свойство, которое сохраняется без компромиссов: **дашборд остаётся read-only**. Привязка к
`127.0.0.1`, точная сверка Host (защита от DNS-rebinding, см. `hostAllowed()` в
`tools/lib/ui-server.mjs`), отсутствие пишущих эндпоинтов — всё это остаётся как есть.

Центр управления показывает правду о системе и даёт средства восстановления (что зависло,
кто молчит, где сбой) — но **не становится пультом необратимых действий**. Действия
исполняются через существующие каналы: `samemind fleet assign`, `ledger append`, inbox
(всё через CLI/MCP), а экран лишь отображает их результат и, при необходимости, готовит
команду для ручного запуска.

## 1. Зачем расширяется дашборд

Сегодня дашборд v1 отвечает на «что есть в памяти» и «кто жив во флоте». Версия 0.16
добавляет два новых источника сигнала: **голосовой контур** (см. `docs/spec/voice.md`) и
**окружающее зрение** (см. `docs/spec/ambient-vision.md`). Чтобы наблюдать за ними из
одного места, нужен единый экран — иначе голос и зрение станут невидимыми подсистемами,
которым доверяешь вслепую.

Кроме того, текущий Overview уже близок к «сегодня»: handoff есть (`/api/handoff`),
открытые сбои есть (`/api/ledger` openFailures), просроченные движки есть (`/api/fleet`).
Центр управления формализует это как отдельный видовой слой и связывает с восстановлением.

## 2. Жёсткие границы (унаследованы + новые)

Унаследовано из `docs/ui-spec.md` §0 без изменений:

- **Read-only.** Ни одного пишущего эндпоинта не добавляется. Все `POST/PUT/DELETE` уже
  сегодня возвращают 405 в `tools/lib/ui-server.mjs` — это остаётся.
- **127.0.0.1 only**, сверка Host. Никакого удалённого доступа к центру управления.
- **Self-contained**, без CDN/внешних шрифтов/внешних сетевых вызовов.
- Рендер markdown и тел концептов — через экранирующий рендерер, без
  `dangerouslySetInnerHTML` без санитайзера; ссылки инертны.

Новые для 0.16:

- **Голос и зрение — тоже read-only на экране.** Карточка подтверждения из
  `docs/spec/voice.md` §3 не «выполняет» действие на сервере дашборда — она готовит
  команду (CLI/MCP), которую пользователь запускает сам, либо действие исполняется
  отдельным голосовым сервисом, а дашборд лишь отображает результат через SSE.
- **Наблюдение за голосом/зрением не включает слежку.** Центр показывает *события*
  (реплика, уверенность, решение политики, реплика зрения), а не сырые потоки. Сырое
  аудио/видео на дашборд не передаётся (см. `docs/spec/ambient-vision.md` §4).

## 3. Четыре вида

Четыре смысловых представления, переключаемых в навигации. Порядок строительства (§4)
определяет, что появляется раньше.

### 3.1 Сегодня — «на чём я стою»

Отвечает на: что активно, что приоритетнее, что блокирует. Источник данных — уже
существующие эндпоинты.

- **Handoff-бриф** из `/api/handoff`: активные задачи, недавние решения, планы в силе,
  последняя сессия. Развёрнутый текст, не только свод.
- **Приоритеты дня** — задачи в статусе in-progress/blocked из `/api/board`, отсортированные
  по давности и наличию блокера (заблокированные — выше).
- **Блокеры** — открытые сбои из `/api/ledger` (`openFailures`) и просроченные движки из
  `/api/fleet` (`overdue`), в одном списке, с возрастом и последним действием.
- **Средства восстановления** — для каждой карточки блокера: что можно сделать (команда
  CLI, готовая к копированию/запуску), не более. Например: «движок X молчит 1200с против
  лимита 600с → `samemind fleet status` проверить, `fleet assign` переназначить».
  Кнопка **не выполняет** — она показывает команду.

### 3.2 Флот — «кто работает»

Расширение существующего экрана Fleet (`docs/ui-spec.md` §3.3), без потери текущего.

- **Движки** — реестр: id, роль, статус, last seen, heartbeat, silence bar (как сегодня).
- **Назначения** — текущие назначения из летописи (топики со стадией `start`/`step`),
  привязанные к движкам. Кто что делает прямо сейчас.
- **Здоровье** — overdue-движки, открытые сбои, heartbeat-нарушения. С цветом, не с текстом.
- **Доказательства** — для каждого назначения ссылка на артефакт: последний коммит, файл,
  хвост прогона (как требует правило «летопись — самооценка, факт — артефакт»). Дашборд
  показывает ссылку/путь, не содержимое артефакта целиком.

### 3.3 Память — «откуда это»

Расширение экрана Memory (`docs/ui-spec.md` §3.2), с фокусом на происхождение и конфликты.

- **Inbox** — записи из `inbox/<agent>.md`, с источником и датой. Inbox — единственный
  пишущий путь samemind; центр показывает очередь на продвижение, не промоутирует сам.
  **Требует нового эндпоинта:** `load()` в `tools/lib/okf.mjs` пропускает inbox без флага
  `includeInbox: true`, и ни один существующий эндпоинт этот флаг не передаёт. Поэтому inbox
  не входит в Шаг 1 (§4) — он добавляется отдельным шагом с новым read-only эндпоинтом
  (например, `/api/inbox`), что явно зафиксировано как исключение из «никаких новых
  эндпоинтов» в Шаге 1.
- **Происхождение** — для концепта: frontmatter `source`, дата создания, кто записал.
  «Почему это выдано» — для результатов поиска: показать, *почему* концепт попал в выдачу
  (BM25-скор / семантическое соответствие / сосед по графу), не просто список.
- **Конфликты** — концепты с отношением `supersedes`, одинаковыми id в разных бандлах
  (project vs global), рассинхронизация. Помечаются явно, авто-разрешения нет.

### 3.4 Голос — «что было сказано и что с этим стало»

Новый экран, зеркало голосового контура из `docs/spec/voice.md`. Только для наблюдения.

- **Состояние прослушивания** — текущий режим (§4 голосовой спеки), активно/пауза/mute,
  индикатор «слышу».
- **Расшифровка** — живая карточка текущей реплики (черновой текст + уверенность), даже
  до подтверждения — чтобы было видно, что расслышано.
- **Подтверждение** — карточка ожидания явного «да» (см. голосовая спека §5), с кнопками
  принять/отклонить (которые взаимодействуют с голосовым сервисом, не с дашборд-сервером).
- **Ответ/итог** — что произошло: статус действия, голосовой итог текстом, метрики
  задержек из голосовой спеки §6.

Сырое аудио здесь не появляется никогда — только текст, уверенность, метрики, статусы.

## 4. Порядок строительства (обязателен)

Строить поэтапно, строго слева направо. Каждый шаг должен быть полезен сам по себе,
без следующего. Прыжок вперёд (добавить действия до read-only правды) — дефект плана.

```
Шаг 1: read-only правда (Сегодня + Флот + Память)
  ↓
Шаг 2: состояние задач и средства восстановления (блокеры + команды)
  ↓
Шаг 3: голосовой экран как наблюдатель (без исполнения с экрана)
  ↓
Шаг 4: (будущее) контролируемые действия через подготовленные команды
```

### Шаг 1 — Read-only правда

Что появляется:
- Вид «Сегодня» (§3.1): handoff-бриф, приоритеты, блокеры — на существующих эндпоинтах.
- Расширение «Флот» (§3.2): назначения и доказательства, на существующих `/api/ledger`,
  `/api/fleet`.
- Расширение «Память» (§3.3): **происхождение и конфликты** — на `/api/concepts`,
  `/api/graph`, `/api/concept/<id>`. Inbox сюда НЕ входит — ему нужен новый эндпоинт
  (§3.3), что противоречит принципу «никаких новых эндпоинтов» в Шаге 1; inbox
  добавляется отдельным шагом после.

Что НЕ появляется: никаких новых пишущих ручек, никаких новых эндпоинтов (меняющих
состояние или read-only). Это consolidation существующих read-only данных в новые
представления. Inbox исключён именно потому, что требует нового эндпоинта.

Приёмка шага 1:
- [ ] Все три вида (Сегодня/Флот/Память) рендерят непустые данные на demo-бандле.
      (Память в Шаге 1 — без inbox: происхождение и конфликты.)
- [ ] Ни одного нового POST/PUT/DELETE — проверка `req.method !== 'GET' → 405` сохранена.
- [ ] Ни одного нового эндпоинта любого типа — inbox отсутствует.
- [ ] На live-бандле (замер из `ui/src/graph.tsx`: 103 узла / 296 рёбер) — загрузка
      графа и доски < 2000 мс.
- [ ] Блокеры и overdue видны в одном месте (вид «Сегодня»), а не разбросаны.

### Шаг 2 — Средства восстановления

Что появляется:
- Для каждой карточки блокера/сбоя — подготовленная команда CLI (текстом, копируемая),
  не исполняемая кнопка.
- Контекст: какой движок молчит, против какого лимита; какой наряд в `fail`/`block`;
  когда последний раз подавал признак жизни.

Что НЕ появляется: автопроцессы, автоэскалация, авто-перезапуск. Решение и запуск — за
человеком, экран лишь убирает рутину «вспомнить, какая команда лечит этот сбой».

Приёмка шага 2:
- [ ] Каждый класс сбоев (overdue, openFailure) имеет предложенную команду восстановления.
- [ ] Команда показана текстом, не скрыта за одной кнопкой «исправить».
- [ ] Запуск команды из интерфейса дашборда невозможен (read-only сохранён).

### Шаг 3 — Голосовой экран (наблюдатель)

Что появляется:
- Вид «Голос» (§3.4) — только отражение состояния голосового сервиса.
- Связь с голосовым сервисом — через тот же SSE-поток событий
  (`/api/events/stream`, уже реализован в `tools/lib/ui-server.mjs`), дополненный
  событиями голосового конвейера (см. голосовую спеку §6).

Что НЕ появляется: карточка подтверждения, которая «выполняет» действие через сервер
дашборда. Подтверждение либо готовит команду (как шаг 2), либо взаимодействует с
голосовым сервисом по его собственному API — сервер дашборда остаётся read-only.

Приёмка шага 3:
- [ ] Экран «Голос» показывает режим, расшифровку, метрики задержек — на тестовых
      событиях голосового сервиса.
- [ ] Сырое аудио не передаётся на дашборд (проверка: в payload событий только текст/
      уверенность/статус, нет аудиоданных).
- [ ] При недоступности голосового сервиса — явный индикатор, не пустой экран.

### Шаг 4 — Контролируемые действия (будущее, не 0.16)

Зарезервировано, не реализуется в этой версии. Идея: подготовленные команды из шага 2
могут запускаться с подтверждения — но это требует отдельного решения о пишущих ручках и
выходит за рамки read-only дашборда. Не строить без явного решения владельца.

## 5. Навигация и компоновка

Унаследовано из `docs/ui-spec.md` §2 (левый сайдбар, коллапсируемый, тема/переключатель).
Новый пункт навигации **Голос** добавляется после **Projects**.

**Граф — это вкладка внутри экрана «Память», а не отдельный пункт меню.** Порядок пунктов:

```
Сегодня · Флот · Память · Projects · Голос
```

Внутри «Память» — вкладки: Концепты / **Граф** / Происхождение / Конфликты (граф
перенесён из отдельного пункта меню `Memory(graph)` во вкладку, как и было в
`docs/ui-spec.md` §3.2: граф — вид внутри экрана памяти, не sibling).

**«Сегодня» — посадочный экран по умолчанию** (вместо текущего Overview). Центр
управления концептуально про «на чём я стою», поэтому landing ведёт туда.
Существующий Overview **не удаляется и не остаётся отдельным пунктом** — его KPI-полоса
(4 stat tiles из `docs/ui-spec.md` §3.1) вкладывается в верх «Сегодня» как сводка
состояния. Отдельного пункта «Overview» в навигации 0.16 нет.

## 6. Безопасность и приватность

- Унаследованная защита: `127.0.0.1`, сверка Host, read-only, экранирующий рендер.
- Голосовой экран: показывает только текст/статус/метрики, никогда — аудио.
- Экран зрения (если добавляется позже, за рамками 0.16): только события и реплики,
  никогда — видео/кадры. См. `docs/spec/ambient-vision.md`.
- Команды восстановления — показываются, не запускаются. Даже если позже появится
  «запуск с подтверждения», он требует отдельного пишущего канала и решения владельца.

## 7. Приёмка (критерии реализации центра управления)

- [ ] Четыре вида (§3) присутствуют и переключаемы.
- [ ] Read-only сохранён: греп по `tools/lib/ui-server.mjs` и новым модулям — ни одного
      пишущего эндпоинта; все не-GET методы возвращают 405.
- [ ] `127.0.0.1` и сверка Host сохранены (`hostAllowed` не ослаблен).
- [ ] Порядок строительства (§4) соблюдён: шаг 1 (правда) до шага 2 (восстановление),
      оба до шага 3 (голос).
- [ ] На demo-бандле все виды рендерят непустые данные.
- [ ] На live-бандле (замер из `ui/src/graph.tsx`: 103 узла / 296 рёбер) — загрузка
      графа и доски < 2000 мс, стабильность (без утечки памяти за 5 мин).
- [ ] Экран «Голос» не содержит сырого аудио в payload событий.
- [ ] Обе темы (light/dark) проходят контраст WCAG AA (унаследовано из ui-spec §0).
- [ ] Пустые состояния (нет флота, нет летописи, голос недоступен) — спроектированы,
      не пустые (наследие ui-spec §5).

## 8. Где хранится состояние

Сам центр управления read-only и не имеет пользовательских настроек в этой версии.
Единственное состояние — выбранный посадочный экран (§5, по умолчанию «Сегодня») —
живёт в **`.samemind/config.json`** в корне бандла, в уже существующем доме конфигурации
(см. `tools/lib/projection-config.mjs`: `schema_version`, двухуровневое слияние
global←project, чтение никогда не пишет, атомарная запись через `atomicWriteFileSync`).
Раздел UI (например, `ui: { landing }`) добавляется по тем же правилам; предпочтения
видов/темы, если появятся позже, идут туда же.

## 9. Открытые вопросы (владельцу)

- Делать ли экран «Зрение» частью центра управления в 0.16, или оставить его на уровне
  голосовых реплик и отдельной панели зрения. Draft: в 0.16 — только голосовой экран;
  зрение — отдельная подсистема со своим индикатором статуса, без полноэкранного вида.
- Готовые команды восстановления (шаг 2) — копировать в буфер или показывать в readonly
  блоке. Draft: readonly блок с кнопкой «скопировать», без авто-запуска.
- Inbox требует нового read-only эндпоинта (`/api/inbox` или иного) — вынести в отдельный
  шаг после Шага 1, с явным решением о форме (один файл-список или группировка по агентам).
